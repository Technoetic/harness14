# Harness14 v4.3.0

Three MoAI-inspired controls extend the existing 14-step workflow.

- **Reviewed requirement coverage:** freeze requirement → acceptance → check IDs before implementation, then bind the returned original-byte SHA256 in quality configuration schema 2. Intermediate quality gates verify the frozen inventory; both Codex and Claude final completion require current independent final QA evidence for every declared requirement.
- **Installed instruction size:** `npm run verify:instructions` checks 56 explicitly registered current14 instruction/companion files, eight declared delivery surfaces and required references. It measures static UTF-8 bytes/Unicode characters, without reading instruction bodies into the report or claiming runtime tokens/billing.
- **Diagnostic comparison:** capture an immutable, tool/configuration/source-bound baseline and compare a later normalized snapshot by diagnostic identity. Equal counts cannot conceal replacement errors. Results remain advisory repair triage; required quality gates are unchanged.

Existing quality configuration schema 1 retains its previous semantics. Historical 20/36/50 profiles and recorded completion receipts remain recoverable. New workflow instructions use schema 2; the inventory establishes completeness only of the explicitly reviewed requirement list.

The controls do not execute test commands during inspection, revert code, start workflows, alter hook trust or authenticate a verifier's identity. Changed configuration/generation, stale QA, unsafe paths and malformed input are rejected. Diagnostics persist message hashes rather than raw messages. Static instruction limits do not permit dropping binding safety obligations.

Implementation inspiration is pinned to MoAI `2aab5f797b75983e132af451da68f69e3426557b`; the source differences and links are in the README and the three companion guides. No upstream Go code or runtime dependency was copied.

Release verification is reported in the public `verification.json`: actual local executions, independent review, source SHA/tree, Git-file inventory, CI jobs and downloadable asset hashes. Initial failing/partial runs are kept distinct from final passing runs. These results do not measure live-model performance or real project effectiveness.
